# SmartVintaAwesomeKit v0.6.0
## Product, UX, and Next-Version Requirements Analysis

**Source analyzed:** `ZipPrompt.md`, treated as a ZIP archive containing the application and its accompanying materials  
**Analysis date:** 2026-08-01  
**Observed product version:** 0.6.0  
**Observed maturity:** Alpha

## Evidence and inference convention

- **Confirmed observation** means the behavior, file, interface, test result, or documentation is present in the supplied application.
- **Inference** means a likely user behavior or need derived from the application’s workflows and developer-tool conventions.
- **Opportunity** means a plausible future direction supported by an observed gap. It is not presented as existing functionality or validated market demand.

The application has no conventional end-user graphical interface. Its practical user interfaces are the command line, generated project tree, configuration files, generated README, FastAPI/OpenAPI interface, Python package APIs, diagnostics, test output, and documentation. UI/UX findings therefore concern terminal interaction, command discoverability, generated-code navigation, feedback, failure recovery, API documentation, and repeated developer workflows.

# 1. Product understanding

## What the application appears to do

SmartVintaAwesomeKit is a Python toolkit and project generator for FastAPI services. It aims to shorten the path from an empty directory to a structured, testable, deployment-oriented API project.

### Confirmed current capabilities

The supplied v0.6 application includes:

- Typer-based project generation with `minimal`, `api`, and `saas` presets.
- SQLite and PostgreSQL configuration choices.
- Atomic project creation, destination conflict protection, `--force`, `--dry-run`, and JSON output.
- Generated FastAPI configuration, async SQLAlchemy setup, health and root endpoints, tests, Dockerfile, environment template, and scaffold manifest.
- An `add-resource` workflow that validates typed fields, previews planned changes, generates an in-memory API route and acceptance test, and registers the router.
- Alembic directory and configuration scaffolding.
- Request-ID middleware scaffolding.
- A `doctor` command for structural and production configuration checks.
- An `inspect` command that detects missing or modified generator-managed files using SHA-256 hashes.
- Stable API error envelopes with codes, field-level validation details, and request IDs.
- JWT, password hashing, OAuth2 abstractions, RBAC, session primitives, and authentication middleware.
- In-memory and optional Redis caching, decorators, invalidation, and statistics.
- Pytest fixtures, factories, mocks, assertions, and plugin registration.
- Rich-oriented CLI support modules for themes, prompts, tables, progress, and skeleton generation.
- README, auth and caching guides, release reports, requirements reports, changelog, and test records.

The current value proposition is no longer merely “generate a FastAPI skeleton.” The application is evolving toward a **developer workflow platform** that creates a project, helps extend it, checks its configuration, tracks generated-file drift, and provides reusable backend infrastructure.

## Likely users

### 1. Solo developers and micro-SaaS builders

**Inference:** They want to reach a running MVP quickly, start with SQLite, add resources repeatedly, then move to PostgreSQL and production deployment without rebuilding the project architecture.

### 2. Small backend teams

**Inference:** They need deterministic generation, consistent project conventions, CI-compatible output, safe incremental changes, and visible drift between generated and developer-modified files.

### 3. Platform or enablement engineers

**Inference:** They may adopt the toolkit as a team standard. They care about reproducible presets, security guardrails, template governance, upgrade safety, compatibility policy, and validation across supported combinations.

### 4. Existing FastAPI application developers

They may consume individual package modules such as authentication, caching, database helpers, testing utilities, pagination, or error handling without using the generator.

### 5. Learners and evaluators

**Inference:** They use the README, generated example resource, `/docs`, and examples to understand the architecture before deciding whether to adopt it.

## Main workflows and usage scenarios

### Workflow A: Evaluate the toolkit

1. Read the README and feature claims.
2. Install the package.
3. inspect command help.
4. Preview a project with `init --dry-run`.
5. Generate an API project.
6. Run tests and open `/docs`.
7. Inspect generated files and decide whether the conventions are trustworthy.

### Workflow B: Create a new service

1. Choose a preset and database.
2. Preview generation.
3. Generate atomically.
4. Copy `.env.example` to `.env`.
5. Install dependencies.
6. Run tests.
7. Start Uvicorn.
8. Open `/docs`.
9. Run `doctor` before deployment.

### Workflow C: Add a resource

1. Decide resource name and field definitions.
2. Run `add-resource --dry-run`.
3. Review planned route and test files.
4. Apply generation.
5. Run tests.
6. Inspect files and adapt business logic.

The workflow reduces route and test boilerplate, but stops before database persistence, schemas by operation, services, migration revisions, update/delete/list behavior, and authorization.

### Workflow D: Inspect project drift

1. Run `inspect` locally or in CI.
2. Review missing and modified generator-managed files.
3. Decide whether changes are intentional.

The current workflow provides visibility but no baseline diff, explanation of expected changes, manifest repair, upgrade plan, or conflict resolution.

### Workflow E: Diagnose production readiness

1. Run `doctor --environment production`.
2. Fix missing structure, `.env`, migration scaffold, or weak JWT secret.
3. Repeat until passing.

The command currently provides a useful foundation, but does not yet verify actual database connectivity, migration head state, Redis connectivity, CORS, debug mode, docs exposure, dependency versions, writable paths, or external service readiness.

### Workflow F: Integrate authentication

1. Configure `AUTH_*` values.
2. Instantiate authentication components.
3. Add middleware and dependencies.
4. Create registration/login/refresh/logout routes.
5. Connect users, roles, and session records to a database.

The package provides many primitives, but users still compose the production journey manually. This is the largest remaining gap between product promise and generated-project experience.

### Workflow G: Cache reads and invalidate writes

1. Select an in-memory or Redis backend.
2. Decorate read operations.
3. configure tags or prefixes.
4. invalidate after write operations.
5. inspect statistics.

The package is capable, but backend ownership and invalidation registries can remain conceptually ambiguous when module defaults and explicit instances are mixed.

# 2. UI/UX analysis

## Strengths

### Safe first-run interaction

Project generation validates inputs, supports preview, avoids silent overwrite, stages output atomically, and prints next steps. These behaviors reduce fear and make experimentation safer.

### Automation-friendly interaction

JSON output, deterministic command flags, manifest metadata, and CI-oriented inspect mode support team and scripted usage.

### Visibility of generated state

The `.smartvinta.json` manifest and `inspect` command give users a concrete answer to “what did the generator create, and has it changed?” This is a meaningful improvement over one-shot scaffolding tools.

### Repeat-work reduction

`add-resource` targets one of the most frequently repeated API-development activities and provides preview, conflict prevention, generated tests, and router registration.

### Better debugging contract

Request IDs and stable error envelopes improve both API consumer experience and supportability. Field-level validation messages make the error response actionable rather than merely descriptive.

### Familiar architecture

FastAPI, Typer, Pydantic Settings, SQLAlchemy, Alembic, pytest, Docker, and OpenAPI follow established ecosystem conventions and reduce relearning.

### Strong quality intent

The repository contains broad tests, release reports, documented regression results, and generated-project acceptance tests. This improves trust even though known failures remain.

## Weaknesses

### The `saas` preset is not yet a true SaaS golden path

The preset name suggests an integrated, database-backed application foundation. In practice, the application still requires users to manually compose registration, login, refresh rotation, persisted session checking, logout, roles, and protected domain routes.

**UX impact:** The user must understand several modules and make security-critical architecture decisions immediately after generation.

### Resource generation stops before real persistence

The generated vertical slice uses an in-memory store. It does not generate SQLAlchemy models, operation-specific Pydantic schemas, service/CRUD layers, migration revisions, list/update/delete endpoints, permissions, or cache invalidation.

**UX impact:** The command demonstrates structure but does not eliminate the highest-volume production boilerplate users are likely to expect from “add resource.”

### Migration support is structural, not operational

The project includes Alembic scaffolding, but the user still lacks a complete migration journey: model metadata integration, revision generation, status, checking for unapplied migrations, upgrade, downgrade, and deployment ordering.

### Two CLI architectures appear to coexist

The archive contains both a top-level `cli.py` implementing the working v0.6 flow and a `cli/` package containing Rich prompts, progress, table, skeleton, theme, and a separate commands module. The documentation and package entry point point to `smartvintaawesomekit.cli:app`, while the coexistence of a module and package with the same import name is structurally confusing and risks import ambiguity.

**UX impact:** Contributors cannot easily tell which CLI is canonical. Features in the Rich CLI package may not be part of the actual user path, while users may read code or docs for commands that are not wired into the installed executable.

### Rich CLI capabilities are not integrated into the main journey

Themes, prompts, tables, progress, and skeleton modules exist, but the primary generator experience remains separate. This produces feature surface without a cohesive interaction model.

### Drift reporting lacks an action path

`inspect` reports clean or drifted state, but users are not told:

- what the original generated content was,
- whether a change is compatible with an upgrade,
- how to accept intentional drift,
- how to regenerate only safe files,
- how to resolve conflicts,
- whether the manifest itself is stale.

### Diagnostics do not yet test real dependencies

The current doctor experience identifies structural and secret issues but can still return confidence without checking the database, migration head, Redis, dependency versions, or application import/start behavior.

### Known failures dilute release confidence

The full suite still records failures around password hashing compatibility, Redis test behavior, and pytest plugin discovery. Even when classified as pre-existing or environmental, repeatedly shipping known red tests makes it harder for adopters to distinguish environmental constraints from product defects.

### Documentation carries historical duplication

The package contains v0.4, v0.5, and v0.6 reports as well as a README that still references v0.5 wording in some sections. Older analysis remains useful, but the current user journey can become harder to navigate when current guidance and historical reports are not clearly separated.

### Some examples appear demonstrative or incomplete

The auth and caching examples are useful conceptually, but the archive representation shows incomplete or flattened implementation sections. Even if this is an archive rendering artifact, executable examples should be verified in CI and labeled clearly.

## Confusing elements

1. **Which CLI is authoritative?** `cli.py` and `cli/commands.py` present different implementations and feature sets.
2. **What does `saas` include?** The preset suggests more integration than it currently delivers.
3. **Is Alembic ready to run?** Files exist, but model metadata and complete async migration behavior are not clearly established.
4. **Is `add-resource` for learning or production?** Its name implies a complete resource, while its implementation is an in-memory route/test slice.
5. **Which RBAC manager applies permissions?** A module-level manager can diverge from an application-created manager.
6. **Which cache owns tags and data?** Decorators, invalidation helpers, and explicit backend instances can be mixed.
7. **What does a clean inspect result guarantee?** It proves checksum consistency against the manifest, not that the project is compatible, runnable, secure, or current.
8. **How should users resolve known environment failures?** Reports list them, but the primary setup path does not fully automate diagnosis or remediation.

## Friction points

### Cognitive load

Users must understand presets, database URLs, migration scaffolding, resource fields, manifests, auth modules, session records, RBAC, cache ownership, deployment configuration, and test extras. The toolkit needs stronger progressive disclosure and a recommended reference path.

### Repetitive work

Users still repeatedly create models, schemas, services, migration revisions, route sets, permission definitions, cache invalidation logic, auth tests, and CI configuration.

### Context switching

Users navigate among terminal output, README, module docs, generated README, release reports, examples, source code, `/docs`, and test logs. The current information architecture remains partly capability-oriented rather than entirely task-oriented.

### Failure recovery

Generation and resource conflicts are handled safely, but dependency failures, migration failures, manifest drift, plugin discovery, Redis availability, and auth setup still require manual diagnosis.

### Upgrade uncertainty

The manifest detects drift but does not answer the next question: “Can I upgrade this generated project safely?”

## Navigation and workflow observations

The best current journey is:

1. preview,
2. generate,
3. configure,
4. test,
5. run,
6. add a resource,
7. inspect,
8. doctor.

The weak transition is between “add a resource” and “build a production application.” The next release should connect this path to persistence, migrations, auth, and CI instead of adding unrelated new modules.

# 3. User behavior analysis

## Likely user habits

The following are **inferences**:

- Users will copy the shortest README command before reading architecture docs.
- Users will choose `api` unless the preset differences are extremely clear.
- Users will expect `saas` to include working authentication and persistence.
- Users will run `add-resource` many more times than `init`.
- Users will edit generated files immediately, making future upgrades conflict-sensitive.
- Users will run `inspect --check --json` in CI once drift is treated as a team policy.
- Users will begin with SQLite and later move to PostgreSQL.
- Users will treat `/docs` as the primary visible interface of the generated backend.
- Users will assume a green `doctor` result means the service is deployable.
- Users will copy auth and cache examples and may accidentally mix application instances with module-level defaults.
- Users will prefer a single recommended path over individually composing all available primitives.

## Repeated actions

- Adding resources and field definitions.
- Creating migrations after model changes.
- Running tests and quality checks.
- Copying environment templates.
- Checking generated-file drift.
- Configuring authentication dependencies.
- Adding protected routes and permission names.
- Creating refresh and logout behavior.
- Adding cache tags and invalidation to resource writes.
- Switching between SQLite, PostgreSQL, local, CI, and production settings.
- Reading error output and correlating it with server logs.
- Updating generated projects when the toolkit version changes.

## Likely pain points

1. “The resource generator created an example, but I still need to build the real database layer.”
2. “The SaaS preset does not give me registration, login, refresh, logout, and sessions.”
3. “I can see drift, but I do not know whether or how to upgrade.”
4. “Which CLI implementation should contributors modify?”
5. “Why is the migration folder present if revisions and metadata are not integrated?”
6. “Does doctor verify real availability, or only files?”
7. “Why does the full suite still finish red?”
8. “Which RBAC/cache instance is actually active?”
9. “Can I add authentication or caching after project creation?”
10. “How do I convert the generated in-memory sample into a production resource?”

## Usage bottlenecks

### Bottleneck 1: Generated example to production resource

The largest amount of remaining manual work occurs after `add-resource`. This blocks daily efficiency because each domain object repeats the same model/schema/service/migration/route/test pattern.

### Bottleneck 2: Project foundation to secure SaaS

Authentication primitives exist, but there is no generated end-to-end flow. Security-sensitive manual composition increases time and error risk.

### Bottleneck 3: Drift detection to safe upgrade

The product detects a problem but cannot yet guide resolution.

### Bottleneck 4: Structural diagnostics to deployment confidence

A project can pass structural checks without proving database connectivity, migration readiness, Redis availability, or application startup.

### Bottleneck 5: Contribution and maintenance

The duplicate CLI architecture and historical tests/documentation increase maintainer cognitive load and risk inconsistent behavior.

## Expected but missing interactions

- `add-resource` with persistence, CRUD selection, migration generation, permission and cache options.
- `add auth` or an actually integrated `saas` preset.
- `db revision`, `db upgrade`, `db downgrade`, and `db status` commands.
- `inspect --diff` showing baseline versus current content.
- `manifest accept` for intentional modifications.
- `upgrade --plan` with safe, conflicting, and manual actions.
- `doctor` dependency connectivity and migration-head checks.
- A single canonical CLI with interactive and non-interactive modes.
- Generated CI workflow using the same local quality command.
- A generated `check` command or task that runs formatting, linting, typing, migration checks, and tests.
- OpenAPI examples for standard errors and auth flows.
- Explicit module maturity labels in CLI help and generated README.

# 4. What should be improved

## Critical improvements

1. **Consolidate the CLI architecture.** Choose one canonical CLI package, migrate all live commands and Rich UX utilities into it, and remove or deprecate the competing implementation.
2. **Make resource generation persistent.** Generate models, schemas, service/CRUD, routes, tests, and migration revisions rather than an in-memory demonstration.
3. **Complete the migration workflow.** Make migrations executable, model-aware, inspectable, and deployment-ready.
4. **Deliver a real SaaS authentication vertical slice.** Generate database-backed registration, login, refresh rotation, logout, current user, sessions, roles, and protected examples.
5. **Resolve the known red suite.** A release pipeline must distinguish optional-dependency skips from real failures and finish green in supported environments.
6. **Turn doctor into a real readiness gate.** Add dependency, database, migration, Redis, configuration, app-import, and security checks.
7. **Make dependency ownership explicit.** Eliminate ambiguous RBAC and cache singletons from the recommended application path.
8. **Generate and validate CI.** Every supported preset and database combination should be generated and exercised in clean environments.

## Medium-priority improvements

1. Upgrade-plan and manifest acceptance workflows.
2. Generated task runner for setup, run, test, lint, type-check, migrate, and check.
3. Curated OpenAPI error and authentication documentation.
4. Structured logs linked to request IDs.
5. Environment profiles for development, test, and production.
6. Incremental feature installation for auth, cache, and testing.
7. Contract-correct async mocks.
8. Compatibility and deprecation policy.
9. Consolidated current documentation with historical reports moved to a versioned archive.
10. CLI performance and narrow-terminal/accessibility tests.

## Nice-to-have improvements

1. Shell completion after command structure consolidation.
2. Organization template overlays after managed-file ownership is stable.
3. Additional deployment targets after one deployment path is continuously validated.
4. Optional observability integrations.
5. Community recipes after official workflows are executable and maintained.

# 5. Requirements

## Priority definitions

- **Must have:** required for a coherent, trustworthy next release.
- **Should have:** materially improves repeated use or team adoption but can follow the core release boundary.
- **Could have:** useful after core workflows are reliable.
- **Won’t have for now:** deliberately deferred to prevent scope dilution.

## Business requirements

### BR-001: Credible golden-path promise

- **Type:** Business
- **Description:** The next version shall offer one documented preset that produces a database-backed, migration-ready, tested API with optional integrated authentication.
- **User value:** Users can evaluate the toolkit through a realistic application rather than disconnected primitives.
- **Priority:** Must have
- **Rationale:** The current product breadth exceeds the integration delivered by generated projects.
- **Acceptance criteria:**
  - A clean generated project installs, migrates, tests, starts, and exposes `/docs` using documented commands only.
  - The generated README states included and excluded capabilities.
  - The workflow passes on every supported Python and database combination.

### BR-002: Green supported-environment release gate

- **Type:** Business
- **Description:** Official releases shall complete all required tests successfully in supported environments, with optional integrations either tested in dedicated jobs or explicitly skipped.
- **User value:** Clear confidence that red tests do not represent hidden product defects.
- **Priority:** Must have
- **Rationale:** Repeated known failures reduce adoption trust.
- **Acceptance criteria:**
  - Core CI has zero failures.
  - Redis tests run in a Redis-enabled job.
  - Password hashing tests run against pinned compatible backends.
  - Plugin discovery tests use environment-independent executables.

### BR-003: Repeat-use efficiency target

- **Type:** Business
- **Description:** A developer shall be able to add a persisted CRUD resource with migration and tests in under five minutes.
- **User value:** Demonstrable reduction in daily boilerplate.
- **Priority:** Must have
- **Rationale:** Resource creation is the highest-frequency post-generation workflow.
- **Acceptance criteria:**
  - Median completion time is below five minutes in usability testing.
  - At least 80% of representative users complete it without undocumented intervention.

### BR-004: Privacy-respecting product measurement

- **Type:** Business
- **Description:** The team shall define opt-in, disabled-by-default measurements for generation success, doctor failures, resource generation, and upgrade-plan completion.
- **User value:** Improvements are driven by actual friction without exposing code or secrets.
- **Priority:** Should have
- **Rationale:** Current prioritization relies mostly on inferred behavior.
- **Acceptance criteria:**
  - Event definitions exclude source, paths, secrets, payloads, and personal data.
  - Users can inspect and disable collection.
  - A non-telemetry feedback path is documented.

## User requirements

### UR-001: One canonical CLI

- **Type:** User
- **Description:** As a developer, I want one consistent CLI so that commands, help, colors, prompts, JSON output, and documentation always agree.
- **User value:** Lower cognitive load and fewer contribution mistakes.
- **Priority:** Must have
- **Rationale:** The archive contains competing CLI module/package structures.
- **Acceptance criteria:**
  - One package owns the installed entry point.
  - All commands share output, error, color, and JSON conventions.
  - Deprecated imports produce actionable warnings for one transition release.

### UR-002: Persistent resource generation

- **Type:** User
- **Description:** As an API developer, I want `add-resource` to create a usable persisted vertical slice so that I do not repeat model, schema, service, route, migration, and test boilerplate.
- **User value:** Faster feature delivery.
- **Priority:** Must have
- **Rationale:** The current in-memory resource is the largest post-generation workflow gap.
- **Acceptance criteria:**
  - Users can select CRUD operations and field constraints.
  - Generated resources persist through the selected database.
  - A migration revision and tests are created.
  - Dry-run and conflict reporting remain available.

### UR-003: Complete SaaS authentication journey

- **Type:** User
- **Description:** As a SaaS builder, I want generated registration, login, refresh, logout, session, role, and protected-route behavior.
- **User value:** Reduces security-critical manual composition.
- **Priority:** Must have
- **Rationale:** The preset name and auth module breadth create this expectation.
- **Acceptance criteria:**
  - The complete journey works against SQLite and PostgreSQL.
  - Refresh rotation and revocation are enforced.
  - OpenAPI supports bearer authentication.
  - Negative security tests pass.

### UR-004: Actionable drift resolution

- **Type:** User
- **Description:** As a maintainer, I want to see what changed and choose to accept, restore, or defer generated-file drift.
- **User value:** Safer upgrades and fewer manual comparisons.
- **Priority:** Should have
- **Rationale:** Detection without a resolution path leaves users blocked.
- **Acceptance criteria:**
  - `inspect --diff` shows baseline and current changes without secrets.
  - Intentional changes can be accepted into the manifest explicitly.
  - No action overwrites a modified file without preview and confirmation or an explicit non-interactive flag.

### UR-005: Real readiness diagnosis

- **Type:** User
- **Description:** As a deployer, I want doctor to verify real dependencies and migration state so that a pass means the service is plausibly deployable.
- **User value:** Faster, safer release preparation.
- **Priority:** Must have
- **Rationale:** File presence alone is not operational readiness.
- **Acceptance criteria:**
  - Database, migration, Redis, import, settings, and security checks are available.
  - Checks are read-only unless explicitly marked otherwise.
  - Every failure includes remediation.

### UR-006: One quality command

- **Type:** User
- **Description:** As a contributor, I want one command to run the same checks locally and in CI.
- **User value:** Less command memorization and fewer CI surprises.
- **Priority:** Should have
- **Rationale:** Daily users repeatedly run tests, linting, typing, and migration checks.
- **Acceptance criteria:**
  - The generated project exposes a documented `check` task.
  - CI invokes the same task.
  - Failure output preserves the underlying tool’s message.

## Functional requirements

### FR-001: Canonical CLI package migration

- **Type:** Functional
- **Description:** Consolidate live commands, Rich output, prompts, progress, tables, skeletons, and shared policy under one CLI package.
- **User value:** Consistent behavior and easier maintenance.
- **Priority:** Must have
- **Rationale:** A module/package naming collision and separate command implementations are present.
- **Acceptance criteria:**
  - Package imports are unambiguous.
  - `init`, `add-resource`, `doctor`, `inspect`, and `version` remain compatible.
  - Help snapshots and JSON schemas are tested.
  - Headless and interactive modes are both covered.

### FR-002: Persistent resource model generation

- **Type:** Functional
- **Description:** Generate a SQLAlchemy model with validated field mapping, primary key, timestamps, and table naming.
- **User value:** Eliminates manual persistence boilerplate.
- **Priority:** Must have
- **Rationale:** Current resources are in-memory only.
- **Acceptance criteria:**
  - Supported fields map consistently on SQLite and PostgreSQL.
  - Invalid or database-incompatible definitions fail before changes.
  - Generated models are imported into migration metadata.

### FR-003: Resource schema and service generation

- **Type:** Functional
- **Description:** Generate create, update, read, and list schemas plus an async service/CRUD layer.
- **User value:** Provides a coherent copyable architecture.
- **Priority:** Must have
- **Rationale:** Routes should not own persistence logic directly.
- **Acceptance criteria:**
  - Optional and required fields behave correctly.
  - Update schemas support partial updates.
  - Service errors map to stable API errors.

### FR-004: Resource route selection

- **Type:** Functional
- **Description:** Allow users to choose create, list, retrieve, update, and delete operations.
- **User value:** Avoids generating unnecessary endpoints.
- **Priority:** Must have
- **Rationale:** Different domain resources need different exposure.
- **Acceptance criteria:**
  - Dry-run identifies every generated endpoint and file.
  - OpenAPI reflects selected operations only.
  - Tests exist for each selected operation.

### FR-005: Migration command group

- **Type:** Functional
- **Description:** Add commands for revision, upgrade, downgrade, current status, and unapplied-migration checks.
- **User value:** Makes schema evolution part of the toolkit workflow.
- **Priority:** Must have
- **Rationale:** Current migration support is only scaffolding.
- **Acceptance criteria:**
  - Commands work from generated project roots.
  - Messages explain missing metadata and connection failures.
  - CI can fail when migrations are unapplied or model changes lack revisions.

### FR-006: Generated initial migration

- **Type:** Functional
- **Description:** Database-enabled presets shall include and apply a valid initial migration.
- **User value:** The first database run is deterministic.
- **Priority:** Must have
- **Rationale:** Empty migration scaffolding creates false readiness.
- **Acceptance criteria:**
  - Fresh databases upgrade to head.
  - Downgrade behavior is documented and tested.
  - SQLite and PostgreSQL jobs pass.

### FR-007: Integrated authentication routes

- **Type:** Functional
- **Description:** The SaaS preset shall generate registration, login, refresh, logout, current-user, session listing, and session revocation routes.
- **User value:** Complete secure onboarding flow.
- **Priority:** Must have
- **Rationale:** Auth primitives exist but are manually composed.
- **Acceptance criteria:**
  - Duplicate identity returns conflict.
  - Generic credential errors avoid account enumeration.
  - All paths use the stable error contract.

### FR-008: Refresh token rotation

- **Type:** Functional
- **Description:** Refresh exchanges shall verify persisted active sessions, issue a new refresh token, and revoke or supersede the previous session.
- **User value:** Logout and compromise controls work as expected.
- **Priority:** Must have
- **Rationale:** Stateless refresh does not enforce session revocation.
- **Acceptance criteria:**
  - Reuse of an old refresh token fails.
  - Expired and revoked sessions fail.
  - Concurrent reuse behavior is tested.

### FR-009: Explicit RBAC registry

- **Type:** Functional
- **Description:** Application permission checks shall use one explicitly configured registry rather than an unrelated module singleton.
- **User value:** Predictable authorization.
- **Priority:** Must have
- **Rationale:** Current manager ownership can diverge.
- **Acceptance criteria:**
  - Registration and checking use the same application-scoped instance.
  - Multiple apps in one process do not share roles unintentionally.
  - Route-level integration tests verify inheritance.

### FR-010: Explicit cache registry and lifecycle

- **Type:** Functional
- **Description:** Cached reads, tags, invalidation, and shutdown shall share an application-scoped backend and invalidation registry.
- **User value:** Reliable cache behavior.
- **Priority:** Must have
- **Rationale:** Module defaults and explicit instances can be mixed.
- **Acceptance criteria:**
  - Generated write operations invalidate affected reads.
  - Redis clients close through lifespan hooks.
  - Multi-process tag behavior is supported or blocked with an explanation.

### FR-011: Doctor connectivity checks

- **Type:** Functional
- **Description:** Doctor shall optionally verify database and Redis connectivity with timeouts and no destructive writes.
- **User value:** Real dependency confidence.
- **Priority:** Must have
- **Rationale:** Current structural checks cannot prove availability.
- **Acceptance criteria:**
  - Each check has pass, warning, fail, duration, and remediation.
  - Credentials are redacted.
  - JSON output has a versioned schema.

### FR-012: Doctor migration and startup checks

- **Type:** Functional
- **Description:** Doctor shall verify migration head state and application import/startup readiness.
- **User value:** Detects deployment blockers early.
- **Priority:** Must have
- **Rationale:** A structurally complete project may still fail at startup.
- **Acceptance criteria:**
  - Pending migrations are reported.
  - Import errors are summarized without default tracebacks.
  - Checks have bounded execution time.

### FR-013: Inspect diff

- **Type:** Functional
- **Description:** Provide a safe textual diff between stored generated baselines and current managed files.
- **User value:** Explains drift rather than only listing it.
- **Priority:** Should have
- **Rationale:** Users need context before accepting or restoring changes.
- **Acceptance criteria:**
  - Binary or sensitive files are excluded.
  - Output supports human and JSON modes.
  - Large diffs are summarized with an explicit detailed option.

### FR-014: Manifest accept and repair

- **Type:** Functional
- **Description:** Allow explicit acceptance of intentional managed-file changes and repair of a damaged manifest.
- **User value:** Keeps drift checks useful after legitimate edits.
- **Priority:** Should have

# 6. New opportunities

## 1. Persistent vertical-slice generator

**Opportunity:** Extend `add-resource` into model, schema, service, migration, routes, tests, permissions, and cache policy.

**Why users may want it:** Resource creation is repeated throughout the life of nearly every generated API.

**Evidence/reasoning:** The existing command proves demand logic and interaction design, while its in-memory limitation is explicitly documented.

## 2. Safe project lifecycle assistant

**Opportunity:** Evolve manifest and inspect into diff, accept, repair, and upgrade planning.

**Why users may want it:** Generated code is edited immediately, making blind regeneration unsafe.

**Evidence/reasoning:** v0.6 already tracks checksums and resources. The next logical value is resolution, not another detector.

## 3. Production SaaS preset

**Opportunity:** Generate a database-backed auth and session journey with migrations, protected example resources, tests, and curated OpenAPI.

**Why users may want it:** Auth is a headline capability, and the preset name creates a strong expectation of integration.

**Evidence/reasoning:** All major primitives already exist separately.

## 4. Compliance-friendly production profile

**Opportunity:** Add doctor policies for secrets, CORS, docs exposure, session TTL, password backend, database encryption expectations, Redis safety, and logging redaction.

**Why users may want it:** Teams need repeatable guardrails before deployment.

**Evidence/reasoning:** Production doctor and stable diagnostics already establish the interaction pattern.

## 5. Team policy presets

**Opportunity:** Allow checked-in generation policy to constrain presets, databases, features, field types, and security defaults.

**Why users may want it:** Platform teams need reproducibility and governance without asking every developer to remember flags.

**Evidence/reasoning:** Deterministic JSON output, manifests, and presets already support policy-oriented usage.

## 6. Contract-tested integration kit

**Opportunity:** Publish protocols and shared behavior suites for caches, auth managers, sessions, repositories, and mocks.

**Why users may want it:** It prevents mocks from drifting from production behavior and makes custom adapters safer.

**Evidence/reasoning:** The testing package is broad, while known async/substitutability issues remain.

## 7. Curated generated developer portal

**Opportunity:** Turn `/docs` and the root endpoint into a compact developer portal showing auth instructions, environments, standard errors, version, readiness, and example journeys.

**Why users may want it:** A generated API’s first visual experience is its OpenAPI interface.

**Evidence/reasoning:** Request IDs, stable errors, tags, and generated resources provide the necessary foundation.

# 7. Final recommendation

## What should be built first

### 1. Consolidate the CLI before expanding it

Resolve the `cli.py` versus `cli/` split and establish one command framework, one output policy, one entry point, and one test surface. Every later workflow depends on this foundation.

### 2. Finish the persistent resource journey

Upgrade `add-resource` from an in-memory example to a database-backed vertical slice with migration and tests. This offers the highest repeated-use productivity gain.

### 3. Make migration support operational

Deliver revision, upgrade, downgrade, status, and model-change checking. Migration scaffolding without an executable lifecycle should not be presented as production readiness.

### 4. Build the real SaaS authentication path

Integrate users, password hashing, token pairs, refresh rotation, session records, logout, roles, and OpenAPI security. This closes the most consequential promise gap.

### 5. Make the supported release matrix green

Resolve password backend, Redis, and plugin-discovery failures. Optional dependencies should be separated into appropriate jobs, not accepted as permanent red results.

## UI and workflow improvements to prioritize immediately

- Task-oriented canonical CLI help.
- A shared plan/apply/summary pattern for every mutating command.
- Stable coded CLI errors with remediation.
- Preset descriptions that accurately state maturity and limitations.
- `inspect --diff` and explicit drift-resolution guidance.
- A generated README tailored to the selected preset.
- Curated `/docs` with error and auth examples.
- Doctor checks that distinguish structural, connectivity, migration, security, and startup status.

## Requirements most likely to improve adoption and efficiency

The highest-impact requirements are:

- **UR-001 / FR-001:** one canonical CLI,
- **UR-002 / FR-002 through FR-006:** persistent resource and migration generation,
- **UR-003 / FR-007 through FR-009:** complete auth and explicit authorization ownership,
- **UR-005 / FR-011 and FR-012:** real readiness diagnosis,
- **BR-002 / FR-017 and FR-018:** a green supported-environment release gate,
- **FR-010 / DIR-003:** explicit and safe cache lifecycle,
- **NFR-001:** generated-project validation matrix,
- **NFR-006:** atomic incremental changes,
- **NFR-008:** executable, current documentation,
- **UX-002 and UX-003:** consistent plans and actionable errors,
- **DIR-005:** versioned manifest contract.

## Recommended release boundary

The next release should ship only when:

1. one canonical CLI owns all live workflows;
2. a generated persistent resource can be migrated and tested;
3. supported CI is green rather than knowingly red;
4. doctor verifies real readiness, not only file presence;
5. the SaaS preset either contains integrated authentication or is renamed/labeled to avoid overpromising;
6. generated projects pass clean installation, migration, test, startup, health, and OpenAPI checks on SQLite and PostgreSQL;
7. README, generated README, help output, and release metadata agree on capabilities and limitations.

The best next-version strategy is not to add more isolated modules. It is to complete the lifecycle already implied by v0.6: **generate, persist, migrate, secure, test, inspect, diagnose, upgrade, and deploy through one coherent developer experience.**
